# 多窗口并行开发与前后端集成规则

> **适用范围**：同时打开两个或更多 Codex/终端窗口推进同一仓库，或前后端并行开发。
> **核心原则**：开发时隔离，契约处交接，集成后入主线。

## 1. 硬性红线

1. **一个可写窗口 = 一个独立 Git worktree + 一个独立分支**。两个窗口不得在同一工作目录
   并行修改文件。
2. **`main` 是稳定集成线**。并行功能不得直接在 `main` 上开发；完成后经集成分支验收，
   再合并到 `main`。
3. **共享或来源不明的脏工作树禁止 `git switch`、`git merge`、`git rebase`、`git stash`
   和 `git add -A`**。先确认每个变更的窗口/任务归属。
4. **只暂存本任务拥有的明确路径**：使用 `git add -- <path...>`，提交前必须检查
   `git diff --cached --name-only` 和 `git diff --cached`。
5. **不得重置、覆盖、移动或清理其他窗口产生的改动**。发现重叠文件立即暂停合并，记录
   冲突并由集成窗口统一处理。

## 2. 会话启动检查

每个准备写文件的窗口在动手前执行：

```bash
git rev-parse --show-toplevel
git branch --show-current
git worktree list
git status --short
```

检查结果必须回答四个问题：

- 当前绝对目录是什么？
- 当前分支是什么？
- 是否有其他窗口使用同一 worktree？
- 工作树中的每个未提交文件属于哪个任务？

只读审计可以共用目录；一旦需要写文件，必须迁移到独立 worktree。新分支默认使用
`codex/` 前缀。

## 3. 前后端契约交接

后端内部实现变化不要求前端逐行跟随；以下变化必须形成一次正式契约交接：

- API 路径、HTTP 方法、请求参数；
- Pydantic/OpenAPI schema；
- 状态、错误码、部分成功和重试语义；
- 时间、来源、证据身份和兼容/退役条件。

交接顺序固定为：

```text
后端 RED 契约测试
  → 冻结 Pydantic/OpenAPI、错误与重试语义
  → 后端原子提交
  → 前端同步 TypeScript、API client、hooks、五态与文案
  → 消费者契约测试 + 浏览器故障注入
  → 集成分支全绿
  → main
```

API 未冻结时，前端任务标记为 `🔒 待上游`。前端可以搭建不含业务字段的状态外壳，
但不得猜字段、伪造数据或把前端接收时间冒充证据时间。

破坏性契约变更与对应前端适配必须进入同一个集成批次。若确需临时兼容新旧协议：

- 兼容分支必须显式可观察，禁止静默回退旧投资数据；
- 写明旧协议退役条件和清理任务；
- 前端迁移完成前，后端不得删除旧接口；
- 兼容层清理纳入五同步和引用清理。

## 4. 跨端问题联合闭环

任一端发现可能跨越 API 边界的问题时，不得直接把问题退回另一端，也不得在各自清单中
建立两个互不关联的待办。先在主管表登记一个 `XI-xxx`（Cross-end Issue）协调编号，再
拆分前端、后端和 QA 子任务。

### 4.1 首报必须包含

| 证据 | 前端负责 | 后端负责 |
|:-----|:---------|:---------|
| 复现身份 | 页面、用户动作、时间、请求 ID/session ID | 对应 trace/request/session ID |
| 输入输出 | 请求参数、HTTP 状态、响应摘要、页面五态 | 路由参数、schema 解析、上游状态和稳定错误码 |
| 时间与环境 | 浏览器、构建版本、是否离线/恢复 | commit、配置版本、数据 `as_of`、Provider 健康 |
| 期望与事实 | 用户看到什么、应该看到什么 | 契约承诺什么、服务实际做了什么 |

证据不完整时允许先登记，并把推断写成 `【推断】`；不得把推断写成已定位根因。

### 4.2 主管与关闭责任

1. 首位主管由问题首先被证明所在的边界决定；暂时无法定位时由集成主管持有，不能让
   前端和后端互相等待。
2. 代码分别归属，问题共同闭环。前端主管负责页面状态与消费者证据，后端主管负责契约、
   数据和运行时证据，QA 独立负责复现与关闭。
3. API 契约尚未确定时先联合复现和定位，再进入 RED 契约冻结；不能为了尽快交接而冻结
   一个尚未理解的问题。
4. 关闭必须同时满足：根因结论、两端子任务、契约/兼容结论、消费者测试和真实浏览器
   复现全部有证据。单端测试通过只能标记“本端完成”，不能关闭 `XI-xxx`。

### 4.3 状态

`🆕 待定位` → `🔎 联合排查` → `🧩 已分责` → `🔧 双端修复` → `🧪 集成验证` → `✅ 关闭`。
若事实证明只影响单端，可在主管表记录证据后转回该端清单，保留 `XI-xxx` 追溯关系。

## 5. 集成分支职责

集成窗口不同时承担功能开发，只负责：

1. 从最新稳定 `main` 创建 `codex/integration-<scope>`；
2. 按“上游后端 → 下游前端”顺序合并原子提交；
3. 只在集成分支解决重叠文件，并记录采用哪一侧语义；
4. 运行后端契约测试、前端测试/类型/构建、浏览器正常与故障路径；
5. 更新工作日志、债务、交接、总清单和旧引用；
6. 全绿后才允许合并到 `main`。

任何一侧单独通过都不等于跨端功能完成。完成定义是“冻结契约 + 两端实现 + 消费者测试 +
真实浏览器验收”同时成立。

## 6. 安全提交模板

```bash
git status --short
git diff --name-only
git add -- path/to/owned-file-a path/to/owned-file-b
git diff --cached --name-only
git diff --cached
git commit -m "<type>: <atomic task>"
```

只有在**确认当前 worktree 为本窗口独占、所有变更均属于同一原子任务**时，才可考虑扩大
暂存范围；项目权威流程不再默认推荐 `git add -A`。

## 7. 已经发生共享脏工作树时

1. 所有窗口先停止新的写操作和 Git 变基/切换/合并；
2. 用 `git status --short` 和 `git diff --name-only` 建立“文件 → 任务/窗口”归属表；
3. 按任务逐个执行路径级测试、路径级暂存和原子提交，禁止一次性收走全部修改；
4. 存在同文件重叠时，不由任一功能窗口擅自提交，转到集成窗口人工合并；
5. 当前批次清理后，后续任务迁移到独立 worktree，不再复用共享目录写代码。
