# 投资有效性优先与组织演进战略设计

> **状态**：设计已形成，等待用户最终审阅后再制定实施计划  
> **日期**：2026-08-07  
> **范围**：产品定位、投资有效性验证、组织归属和慢迁移纪律  
> **不在本轮范围**：代码搬迁、目录重排、功能删除、评测平台建设

## 1. 战略背景

litchi-head 已经具备多 Agent 辩论、动态权重、反思、风控、交易计划、回测、复盘和
多源证据等较完整的工程能力。当前最大的产品缺口不是功能数量，而是尚未用统一、可复现、
含成本的比较证明：完整系统相对单 Agent、简单规则和买入持有产生了多少增量价值。

项目因此从“继续扩展架构”转向“先证明现有架构”。当前原子任务 KR-3B-2 完成后，暂停
新增 Agent、层级和市场，把投资有效性验证与消融实验提升为最高 P0。KR-3B-2 仍需完成，
因为稳定失败诊断和完整失败分母是可信实验的前置条件。

## 2. 产品北极星

litchi-head 的核心产品定义调整为：

> 用可追溯证据、明确分歧、风险边界、置信度校准和历史可靠性，帮助用户进行投资研究与
> 决策；最终拍板和下单属于用户。

产品价值不再用“有多少层、多少大师、多少功能”衡量，而用相对简单替代方案的净增益衡量。
净增益同时包括预测质量、经济结果、安全性、运行质量和总成本。

大师人格保留为用户容易理解的表达层。底层逐步以可检查的策略原型描述能力，例如
`value`、`quality`、`growth`、`momentum`、`macro`、`event_driven`、`contrarian` 和
`statistical`。系统不宣称模拟真实人物本人。

## 3. 四条共同战略方针

1. **证据先于扩张**：新增复杂度前必须声明准备改善的指标、验证方法和失败后的处置。
2. **比较产生价值**：功能存在和测试通过只证明功能账，不证明投资效果账。
3. **简单替代优先**：完整系统必须同时面对现金/不行动、买入持有、简单规则和单 Agent。
4. **人负责拍板**：系统输出研究证据、情景和风险，不把未验证结论包装成确定性荐股。

## 4. 最小验证闭环

项目不建设新的大型模型治理平台。首轮只复用现有能力：

- `src/backtest/` 已有 Sharpe、最大回撤、胜率、盈亏比和 CAGR；
- `src/debate/trust.py` 已有 Brier score 和 calibration curve；
- `src/retro/` 已有推荐与实际结果记录；
- K 线证据链正在提供点时、版本化、可回放的数据；
- `python scripts/check.py --full` 已提供软件质量闸门。

首轮最小闭环只包含：

1. 冻结一批 `DecisionSnapshot`；
2. 同场运行完整版、单 Agent、简单规则和买入持有；
3. 统一计算预测、经济、安全、运行和成本指标；
4. 对主要层级进行单变量消融；
5. 产出一张含样本量、置信区间、失败分母和限制说明的比较表；
6. 根据证据决定保留、简化、关闭或复验。

评测协议继续以
[DECISION_BASELINE_AND_SHADOW_VALIDATION.md](DECISION_BASELINE_AND_SHADOW_VALIDATION.md)
为唯一指标口径事实源。本设计只改变其优先级、治理方式和启动顺序，不复制第二套指标定义。

## 5. 轻量治理模型

采用“中央定方向、统一协议裁判、部门自主作战”，但不建立常设委员会或审批系统。

### 5.1 中央只决定

- 产品北极星和对外承诺；
- 正式主 baseline、样本范围、成本口径和转段标准；
- 与资金、仓位、停止线、生产数据源和合规定位有关的决定；
- 是否根据最终证据删除具有明显产品影响的核心能力。

### 5.2 能力域自主决定

- 模块内部算法、代码结构和技术实现；
- 不改变冻结口径的探索性实验；
- 降低成本、延迟和运维复杂度的方法；
- 提出合并、关闭或替换自身能力；
- 对异常结果提出一次有明确理由的预注册复验。

### 5.3 统一协议负责裁判

- 回测研究维护统一计算口径、baseline 编排和配对比较；
- 投资效果验证检查数据泄漏、删样、版本漂移和统计复现；
- 各业务能力域不能自行更换正式样本、指标、成本或结果分母；
- 消融首次失败先检查样本量、市场状态和实现缺陷；有理由时允许一次预注册复验；复验仍无
  增益时默认关闭或移出核心链路。

这里的“裁判”是冻结配置、可重复命令和报告，不是新增管理层。

## 6. 组织现状审计

当前 11 个平级部门能够覆盖功能范围，但已经出现以下问题：

- 部门文档共 47 个 Markdown、约 5350 行，多数 `ROLE.md` 自 2026-06-21 后未更新；
- `src/callback/` 和 `src/retro/` 有实际业务，却没有清晰部门归属；
- AI Agent、辩论和记忆同时拥有“大师人格/角色”相关职责；
- 基础设施与 QA 对测试配置、CI 和运行环境存在交叉；
- 数据部旧“静默降级”规则与当前正式证据失败关闭相冲突；
- 基础设施旧多 Provider 描述与当前 DeepSeek 单 Provider 策略不一致；
- 风控、交易和 AI Agent 具有专业边界，但当前规模不足以承担完整平级部门治理成本。

因此组织覆盖基本完整，但边界已经不够经济，也存在规则漂移和无人归属。

## 7. 七个能力域

本设计把当前 11 个平级部门逻辑收敛为七个能力域。第一阶段只改变治理归属，代码和文档路径
保持原位。

| 能力域 | 当前代码/职责范围 | 结论 |
|:-------|:------------------|:-----|
| 数据与证据 | `src/data/` | 独立保留；拥有最大数据资产和最高完整性风险 |
| 决策智能 | `src/agents/`、`src/core/`、`src/debate/` | 合并 Agent 架构与辩论；Agent 是决策系统的能力组件 |
| 记忆与反馈 | `src/memory/`、`src/callback/`、`src/retro/` | 重组并补齐 callback/retro 的归属 |
| 风险与执行模拟 | `src/risk/`、`src/trader/` | 组织合并；风控与交易代码、红线继续隔离 |
| 评测研究 | `src/backtest/`、投资效果验证 | 强化 baseline、消融、统计和复现职责 |
| 产品交付 | `backend/`、`frontend/` | 后端和前端作为专业子组，共同对用户可见结果负责 |
| 平台运行 | `src/utils/`、CI、软件质量 | 合并运行基础设施和软件质量闸门 |

`00-cross-cutting` 改为战略事实源，不再视为生产部门。原质量保障职责拆分：软件 CI 和构建
归平台运行；投资实验的防泄漏、复现和统计验收归评测研究。

## 8. 责任守恒映射

组织合并不能造成业务丢失。第一阶段必须保留以下映射：

| 现有职责 | 新归属 |
|:---------|:-------|
| Agent 基类、通信协议、MasterAgent、辩论、评审、权重、置信度 | 决策智能 |
| 大师人格和策略原型定义 | 决策智能主责；记忆与反馈保存版本 |
| MemoryStore、知识库、CallbackEngine、M3-EXT、Retro Board | 记忆与反馈 |
| 风控辩论、确定性硬门禁 | 风险与执行模拟的风控子组 |
| TradePlan、执行步骤和成交模拟 | 风险与执行模拟的交易子组 |
| Backtest、baseline、walk-forward、消融和统计报告 | 评测研究 |
| API、持久任务、界面和四态展示 | 产品交付的后端/前端子组 |
| LLM、配置、成本、日志、CI、构建和软件测试闸门 | 平台运行 |
| 所有开放技术债务 | 随职责映射；原 ID、历史和状态保持不变 |

每项职责必须有且只有一个主责能力域，可以有配合方，但不能无人负责或多头裁决。

## 9. 业务不丢失的五项验收

1. **功能守恒**：现有入口、行为和输出不因组织调整而改变。
2. **接口守恒**：所有提供方和消费者仍有明确负责人。
3. **债务守恒**：每个开放 TD 都有唯一新归属，不丢失、不复制新 ID。
4. **规则守恒**：有效红线全部进入新归属；过时规则显式修订，不能静默消失。
5. **证据守恒**：测试、日志、ADR、学习卡片和历史交接继续可追溯。

反向检查同样必须执行：每个新能力域声明的职责必须能指向现有代码、文档或明确批准的战略
任务，不能凭空创造组织故事。

## 10. 组织存在价值评判标准

每个候选独立能力域按七项评估，每项 0～2 分：

1. 是否有不可被相邻组织自然吸收的独立结果责任；
2. 是否拥有明确代码、数据、协议或运行资产；
3. 是否经常需要独立的专业判断；
4. 是否承担必须相互制衡的资金、安全或验证风险；
5. 是否通过稳定契约服务多个上下游；
6. 是否有自己的长期 backlog 和演进节奏；
7. 分离减少的认知负担是否大于文档、同步和协调成本。

解释区间：

- 10～14：适合独立能力域；
- 6～9：作为专业子组；
- 0～5：合并或删除；
- 安全制衡可以覆盖分数，但必须指出具体风险和隔离机制。

满足以下任意两项时触发合并审查：连续两个阶段无独立交付、80% 以上任务与另一组织共同
发生、没有独立消费者、职责可被相邻组织完整覆盖、文档持续与代码或战略不一致、无法定义
自身价值指标。

该检查只在 Phase 转段、准备新增组织或出现明显职责冲突时进行，不新增固定周期会议。

## 11. 慢迁移纪律

大动作搬家必须慢。采用四阶段、每阶段可独立停止的迁移方式：

### 阶段 O0：冻结与映射

只建立当前组织、职责、接口、债务和规则清单，不改路径。

### 阶段 O1：逻辑归属

只更新组织总览和战略事实源；旧部门目录保留，标记为七个能力域下的专业子组或历史责任
入口。现有代码、API、模型、测试和债务不动。

### 阶段 O2：运行观察

至少运行一个完整阶段，观察新归属是否减少重复加载、文档漂移和多头决策。如果没有明确
收益，停止迁移并保留现有物理结构。

### 阶段 O3：可选物理整理

只有在 O2 证明物理结构仍造成持续成本时，才单独提出迁移设计。实施前必须具备：完整引用
清单、逐文件去向、自动化引用检查、全量测试、明确回滚点和用户再次批准。

任何阶段都不得以“组织合并”为理由顺便删除业务功能或改变产品行为。

## 12. 执行顺序

1. 完成 KR-3B-2，确保正式实验拥有稳定失败分类和完整分母；
2. 执行 O0 责任守恒清点；
3. 执行 O1 逻辑归属，不搬代码和目录；
4. 修订 TD-074 协议的启动顺序，冻结首轮最小实验；
5. 建立最小 DecisionSnapshot、四组 baseline 和单张结果表；
6. 先回答完整版是否优于简单替代，再决定 KR-4～6 的范围；
7. 一个阶段后审查 O2，物理迁移仍需新的用户决策。

## 13. 明确不做

- 不新增部门、常设委员会或审批服务；
- 不立即重排 `src/`、`backend/`、`frontend/` 或部门文档目录；
- 不为首轮实验建设通用模型治理平台；
- 不在第一张可信比较表之前扩大师、扩层或扩市场；
- 不用组织调整掩盖 TD-061、TD-067、TD-072、TD-074 等真实债务；
- 不把小样本、回测或功能测试宣传成真实投资效果已经得到证明。

## 14. 设计验收标准

后续实施计划必须证明：

- 七个能力域覆盖全部现有职责、接口和开放债务；
- 新结构没有新增代码迁移或运行时依赖；
- TD-074 仍是唯一评测口径事实源；
- 首轮实验能复用现有回测、校准、复盘和 K 线证据能力；
- 部门自治不包括修改冻结实验口径；
- 物理迁移必须经过 O2 观察和单独批准；
- 项目能在最短路径上产出第一张可信对比表，而不是新增另一座工程大山。
