###### TD-061 结果参数回调引擎缺失 — 结果来了，大部分相关策略不响应

| 属性 | 值 |
|------|-----|
| **分类** | `架构设计` `severity:critical` `module:all` `impact:功能缺失` |
| **发现日期** | 2026-06-23 |
| **发现人** | 用户审视 |
| **状态** | `🔧 修复中`（RC-001/RC-002 已完成，用户行为和风控回调待接入） |
| **本金估算** | ∼3-4天（核心引擎+三大回调实现） |
| **日利息** | 各大师对特定板块的误判永远不会被校准；用户的个人行为经验永远进不了辩论；风控策略不会根据近期结果自适应 |
| **实盘影响** | **不修则无法形成"投研闭环"** — AI 建议再好，用户操作不听也不知道为什么。系统永远学不到用户的习惯和偏差 |
| **触发场景** | 每次用户决策后、每次市场结果出来后 |
| **用户能发现吗** | 能 — 体现在"AI 永远在重复同样的错误"、"理财经理从用户的操作中学习不到东西" |

**描述**：
M2 反思（AI vs 市场）和 M3 信任度（大师权重统计）都只覆盖了"结果反馈"的一个极薄子集。缺少统一的"结果参数回调引擎"——当任一结果到达（市场结果、用户操作结果），自动触发全链路策略参数校准。

**具体问题**：
1. ❌ M3 只调大师投票权重——不调大师对特定板块的置信度基准、不调分析师层指标权重、不调风控参数
2. ❌ 用户的操作（买/卖/持有/放弃）完全没被追踪——不知道用户是否采纳了 AI 建议、用户的实际盈亏如何、用户的决策模式是什么
3. ❌ 没有统一的 `ResultCallbackEngine`——每个需要响应结果的模块都得自己"等结果"，没有注册-订阅-分发机制

**利息分析**：
- 日复一日，系统不会越来越懂用户的个人习惯——永远处于"冷启动"状态
- 某大师在科技股连续亏 → 权重只会轻微下调，但它在科技股发言时依然 100% 置信度——应该先校准它在科技股场景下的可信度
- 用户每次在 AI 说"持有"时提前卖出 → 系统永远学不到用户的这个倾向

**修复方向**：
设计一个 `ResultCallbackEngine` 统一接收结果事件 → 分发到注册的回调处理器 → 各回调按需调整策略参数。同时扩展 M3 的 `AgentOutcome` 到按板块/场景细分统计。

**进展记录**：
- 2026-07-10：RC-001 核心分发器完成。`src/callback/engine.py` 已支持事件分发、回调注册、优先级、冷却、错误记录、自动禁用、执行记录持久化；`tests/test_callback/test_engine.py` 覆盖 5 条核心路径。
- 2026-07-10：RC-002 回调层完成。`AgentOutcome.sector`、按板块胜率、`m3_ext` 结果回调已上线。
- 2026-07-13：RC-002 编排器 dispatch 完成。`DebateOrchestrator.reflect_on_decision()` 收到 `ActualOutcome` 后分发 `ACTUAL_OUTCOME_RECEIVED`，M3-EXT 会把历史 `agent_analyses` 与实际结果写入 TrustTracker；复盘看板入口仍待接入。
- 尚未关闭：RC-003 用户行为追踪、RC-004 风控参数自适应、R4 交易复盘等业务闭环尚未接入，系统还不能完整按用户操作和实际盈亏自动学习。

###### TD-077 会话快照若跨越信任边界需重评目录存储安全性

| 属性 | 值 |
|------|-----|
| **分类** | `安全边界` `severity:low` `module:cross-cutting` `impact:恢复缓存隔离` |
| **发现日期** | 2026-08-12 |
| **发现人** | Task 5 范围复盘 |
| **状态** | `📋 条件触发时重开` |
| **本金估算** | 触发后重新做威胁建模与独立安全设计评审 |
| **日利息** | 当前若误把可信本机用户缓存宣传为跨账号或特权服务的安全边界，会在部署变化时留下错误保证 |
| **实盘影响** | 当前无直接实盘决策影响；若把含敏感恢复内容交给不可信或共享服务，快照可能被非预期主体读取或重定向 |
| **触发场景** | 快照跨信任边界共享、包含敏感材料，或由特权/共享服务运行 |
| **用户能发现吗** | ❌ 通常不能；必须在架构变更评审中主动重开 |

**描述**：

当前实现的边界是可信本机用户：保存和发现会拒绝验证时已经存在的 symlink/junction/reparse
目录组件，并在不确定时回到只读仓库恢复；它不试图抵御同一账号在校验后原地替换普通目录的
并发进程。真实预存 junction 逃逸证据说明基线需要该最小保护，但不证明需要完整原生目录后端。

**具体问题**：

1. ❌ 若快照被共享给不同信任主体，当前产品边界不再足够；
2. ❌ 若快照承载敏感材料或由特权/共享服务运行，需要重新评估权限、目录句柄与审计需求；
3. ❌ 未提交的 Round 5 原生后端曾尝试扩大这一范围，已撤销 983 行新增和 58 行删除，且从未提交或发布。

**利息分析**：

- 只要部署仍是可信本机用户、快照仍是可丢弃缓存，预埋 NT handle-relative 复杂度没有相称收益；
- 一旦触发条件成立，沿用本结论会把“失败关闭”误当成跨边界隔离保证。

**修复方向**：

仅在触发场景出现时重开本债务，先完成新的信任边界与敏感性评审，再决定是否需要
handle-relative 存储、服务隔离或其他平台级控制；当前不实现或宣称这些能力。

###### TD-078 v2 快照载入未重新执行凭据扫描且扫描契约覆盖不足

| 属性 | 值 |
|------|-----|
| **分类** | `安全边界` `severity:important` `module:cross-cutting` `impact:凭据泄漏` |
| **发现日期** | 2026-08-12 |
| **发现人** | Task 7 独立安全复审 |
| **状态** | `📋 已确认` |
| **本金估算** | ∼0.5-1d（冻结扫描契约、载入复扫、回归与复审） |
| **日利息** | 每次载入手工构造或被替换的 schema-valid v2 快照，都可能绕过保存时扫描并把敏感值输出到终端或 JSON |
| **实盘影响** | 不直接改变投资结果，但可能泄漏 API/数据库凭据，继而影响数据源、LLM 服务和账户安全 |
| **触发场景** | session root 中出现未经过官方 `save` 路径写入、或保存后被替换的合法 v2 JSON；敏感材料使用当前扫描器未覆盖的 PEM、连接串、AWS 或 GitHub 形式 |
| **用户能发现吗** | ❌ 通常不能；快照结构仍合法，敏感值可能只在恢复输出或日志中暴露 |

**描述**：

`load_v2` 当前只做结构校验，不重新执行凭据扫描。独立复审已证明，手工构造的 schema-valid
v2 快照可通过文本和 JSON 报告暴露一个扫描器可识别的 token；同时现有扫描规则对常见 PEM、
连接串、AWS 和 GitHub 凭据形式没有明确覆盖，扫描器究竟保证什么也尚未形成冻结契约。

**具体问题**：

1. ❌ 写入路径通过扫描不代表后续载入的文件仍可信；
2. ❌ 人工或外部写入的合法 v2 快照可以绕过保存时门禁；
3. ❌ 凭据模式覆盖与误报边界没有可审计的契约和测试矩阵。

**利息分析**：

- 恢复入口越普及，未经复扫的载入面越容易成为凭据回显通道；
- 继续零散追加正则会扩大误报/漏报的不确定性，且难以判断何时可以关闭债务。

**修复方向**：

先冻结允许内容与拒绝模式的最小扫描契约，再让官方保存和 `load_v2` 共用同一实现；对文本、
JSON、人类报告和常见凭据族补 RED→GREEN 回归，并经独立安全复审后关闭。

###### TD-079 `exact_next_step` 允许控制字符伪造校验器输出行

| 属性 | 值 |
|------|-----|
| **分类** | `输入契约` `severity:important` `module:cross-cutting` `impact:恢复指令完整性` |
| **发现日期** | 2026-08-12 |
| **发现人** | Task 7 独立安全复审 |
| **状态** | `📋 已确认` |
| **本金估算** | ∼0.5d（字段约束、渲染防御、回归与复审） |
| **日利息** | 恶意或损坏快照可伪造额外 `STATUS`、`DIAGNOSTIC` 或 `NEXT STEP` 行，削弱机器与人工对校验结果的信任 |
| **实盘影响** | 间接影响实盘可靠性；伪造的恢复输出可能诱导后续代理执行错误任务或误判仓库状态 |
| **触发场景** | `HandoffPayload.exact_next_step` 含 CR、LF、DEL 或其他控制字符，并进入人类可读报告 |
| **用户能发现吗** | ❌ 不一定；伪造行与校验器的真实输出格式相同，看起来可能完全正常 |

**描述**：

`HandoffPayload.exact_next_step` 目前只要求非空，允许 CR/LF 和其他控制字符。该值在 `MATCH`
报告中直接拼接到 `NEXT STEP:`，因此可以注入看似由校验器生成的新输出行。

**具体问题**：

1. ❌ Pydantic 契约没有拒绝换行和不可见控制字符；
2. ❌ 人类文本报告没有第二层单行编码/转义保证；
3. ❌ 当前测试未冻结“每个机器可识别字段只占一行”的输出不变量。

**利息分析**：

- 任何基于逐行解析的 Skill 或人工操作都会持续暴露在输出混淆风险下；
- 后续新增报告字段会扩大可伪造的语义空间。

**修复方向**：

在模型边界拒绝全部 CR/LF/控制字符，并让文本渲染层保持防御性单行输出；补充模型、CLI 文本和
JSON 行为的 RED→GREEN 回归，再做独立安全复审。

###### TD-080 legacy 候选读取可跟随 session root 外的目录重定向

| 属性 | 值 |
|------|-----|
| **分类** | `安全边界` `severity:moderate` `module:cross-cutting` `impact:越界读取` |
| **发现日期** | 2026-08-12 |
| **发现人** | Task 7 独立安全复审 |
| **状态** | `📋 已确认` |
| **本金估算** | ∼0.5d（候选身份约束、平台回归与复审） |
| **日利息** | 每次扫描 legacy 历史候选都可能访问 session root 外的文件，扩大只读恢复的文件系统读取边界 |
| **实盘影响** | 不直接改变投资结果，但可能读取并处理非预期本机文件，破坏恢复工具的最小权限和隐私边界 |
| **触发场景** | legacy `*-session.tmp` 候选或其父目录在扫描前已是指向 session root 外部的 symlink/junction/reparse 重定向 |
| **用户能发现吗** | ❌ 通常不能；legacy handoff 虽被隔离，扫描和读取动作本身不会在正常输出中显式呈现越界路径 |

**描述**：

Task 7 复审确认 legacy 发现/读取仍会跟随预先存在的 symlink/reparse 候选到 session root 外。
legacy handoff 继续保持隔离、不会授权下一步，因此风险低于 v2 指令暴露，但读取边界仍与当前
可信本机用户设计所声明的 session root 范围不一致。

**具体问题**：

1. ❌ legacy 候选在读取前未可靠证明最终文件仍位于 session root 内；
2. ❌ Windows junction/reparse 与 POSIX symlink 的回归矩阵未覆盖该读取路径；
3. ✅ legacy 内容仍只能产生 `LEGACY_UNVERIFIABLE`，不会暴露可执行 handoff。

**利息分析**：

- 保留 legacy 兼容越久，隐式越界读取面存在越久；
- 若未来扩大 legacy 解析内容，当前中等风险会随可观察数据增加而上升。

**修复方向**：

在 legacy 发现和读取前验证候选及其目录组件没有逃出 session root，并在能力不足或身份不确定时
跳过/失败关闭；补 Windows reparse 与 POSIX symlink 回归，再经独立安全复审关闭。
